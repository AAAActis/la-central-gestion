## 1 · Historia

**Como** Integrante del equipo  
**Quiero** comprender y documentar la estructura del código generado con asistencia de IA  
**Para** poder explicar y defender cada decisión de diseño del frontend ante el tutor y el tribunal

## 2 · Precondiciones

HU-UI-01 a HU-UI-13 implementadas

## 3 · Criterios de aceptación

| ID | Dado que | Cuando | Entonces | Tipo | Prueba |
|---|---|---|---|---|---|
| **CA-001** | Dado que el frontend está construido | cuando se revisa su estructura | entonces el equipo documenta qué responsabilidad cumple cada carpeta y cada tipo de archivo del proyecto | + | Pendiente |
| **CA-002** | Dado que se emplea un mecanismo del framework que el equipo no escribió a mano | cuando se revisa el código | entonces el equipo lo documenta explicando qué hace y por qué está ahí, con la referencia bibliográfica que lo respalda | + | Pendiente |
| **CA-003** | Dado que un integrante no puede explicar una porción del código | cuando se realiza la revisión cruzada | entonces esa porción se estudia, se reescribe o se descarta antes del cierre del sprint | − | Pendiente |
| **CA-004** | Dado que se completa la documentación | cuando se realiza la revisión final | entonces cada integrante puede explicar el flujo completo de una operación desde la pantalla hasta la API | + | Pendiente |

**Cantidad de criterios: 4.**

## 4 · Notas

HU de control, no de funcionalidad. Su criterio de aceptación es la capacidad de explicación del equipo, no la existencia del código. Sin ella, el uso de asistencia por IA queda sin respaldo verificable en la defensa. El CA-003 es deliberadamente exigente: código que nadie puede explicar no se entrega.
