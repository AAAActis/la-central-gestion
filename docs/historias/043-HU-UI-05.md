## 1 · Historia

**Como** Usuario del sistema  
**Quiero** cargar y modificar datos con un mismo comportamiento en todos los módulos  
**Para** que las validaciones y los mensajes de error sean predecibles en todo el sistema

## 2 · Precondiciones

La API expone los endpoints de alta y modificación

## 3 · Criterios de aceptación

| ID | Dado que | Cuando | Entonces | Tipo | Prueba |
|---|---|---|---|---|---|
| **CA-001** | Dado que todos los campos obligatorios están completos y son válidos | cuando el usuario guarda | entonces el sistema envía los datos y confirma la operación | + | Pendiente |
| **CA-002** | Dado que un campo obligatorio está vacío o tiene formato inválido | cuando el usuario intenta guardar | entonces el sistema bloquea el envío e indica el campo con su error, sin llamar a la API | − | Pendiente |
| **CA-003** | Dado que la entidad admite datos multivaluados (teléfonos, direcciones, códigos) | cuando el usuario agrega o quita uno | entonces el sistema actualiza la lista sin afectar el resto del formulario | + | Pendiente |
| **CA-004** | Dado que la API rechaza la operación por una regla de negocio | cuando se recibe la respuesta | entonces el sistema muestra el motivo devuelto por el servidor junto al campo correspondiente | − | Pendiente |

**Cantidad de criterios: 4.**

## 4 · Notas

La validación del cliente no reemplaza la del servidor: la API valida siempre, y el formulario solo evita llamadas innecesarias.
